编制日期：2026-10-22；实施更新：2026-10-23。本文保留最初的设计分析，第二阶段功能现已实现，原库已在自动备份后完成兼容迁移。实际实现、验证和回滚入口见《第二阶段实施与验收.md》。

实施细化：问卷内的临时题目允许在草稿中直接编辑，只有“保存到题目中心”或发布时才生成正式不可变版本，避免自动保存每次击键都创建新版本；正式题目的工作草稿与历史版本分开存储。发布时自动封存的临时题目默认不列入题目中心，可由作者主动保存展示。原始答卷不回填字段，旧身份通过独立关联集合解析。

## 2. 八项需求逐条落地

1. **常用题目保存与复用**：建立“我的题目”入口，支持独立创建，也支持从问卷中保存题目；引用时记录同一个 `question_version_id`，不能只复制一份无来源文本。
2. **题目分享给其他用户**：按用户授权查看和使用指定版本；接收方把该版本加入自己的问卷。题目所有权不转移，也不自动开放答卷数据。
3. **修改不影响已发布问卷**：正式题目版本不可变，已发布问卷的题目结构永久锁定；改题生成新版本，旧问卷继续引用旧版本。修改已发布问卷的结构通过“复制为新草稿”完成。
4. **修改历史与恢复**：保存父版本、创建者、修改说明及恢复来源；历史可比较。恢复旧内容生成一个新版本，不覆盖旧记录。
5. **多个版本同时存在**：一个逻辑题目下可有多个版本及分支；每份问卷绑定明确版本，发布新版本不会自动替换其他问卷的绑定。
6. **查询题目使用情况**：分别按具体版本和整个题目系列查询使用它的问卷，并按草稿、已发布、已关闭分类。编辑前展示影响范围及版本选择。
7. **题库管理**：支持题库创建、改名、归档、加入题目和移除题目；题库条目固定一个推荐版本，版本升级由用户明确选择。
8. **跨问卷单题统计**：按全局版本标识汇总所有有统计权限的问卷；整个题目系列默认按版本分组，明确统计范围、样本量及版本差异。

## 3. 先分清四种标识

- `question_series_id`：逻辑题目系列，例如“年龄题”，用于组织历史版本。
- `question_version_id`：一份已保存、不可变的题目内容，用于复用、发布和精确统计。
- `qid`：题目在某份问卷中的实例标识，继续用于答案键和跳转目标。
- `surveys.version`：问卷编辑乐观锁，不是题目业务版本号。

例如，问卷 A 的 `q3` 和问卷 B 的 `q1` 都可以引用同一个“年龄题 v1”；问卷 C 的 `q2` 引用“年龄题 v2”。A 与 B 可以直接做同版本统计，C 的结果先单独展示。

不能用 `qid=q1`、相同题目标题或相同内容摘要认定为同一道题。不同问卷的 `q1` 可能完全无关，两道同名题也可能有不同含义。

### 3.1 可复用内容与问卷实例配置分离

正式版本保存题型、题干、选项及答案约束：`type / title / options / min_select / max_select / text_min_len / text_max_len / num_min / num_max / integer_only`。

`qid / order / required / jump_rules` 属于问卷实例。特别是跳转目标只在当前问卷内有意义，不能把某份问卷的 `goto=q5` 当作题目模板带入其他问卷。

从题库导入时生成当前问卷内唯一的 `qid`；完整复制问卷时保留或统一重映射所有 `qid` 及跳转目标。替换版本可保留该位置的 `qid`，但必须重新校验整卷：选项或题型改变可能使原有跳转条件失效，不能静默删除规则。

## 4. MongoDB 数据结构调整

保留原有四集合，新增四个业务集合。题目内部的选项和约束仍作为一个文档保存，不拆成关系表式的多层实体。

### 4.1 question_series 逻辑题目与可变元信息

保存 `_id / owner_id / name / tags / default_version_id / next_version_no / revision / archived_at`，以及共享授权。

共享授权可内嵌为 `shared_with`，每条包含 `user_id`、可使用的版本范围及是否允许派生。默认分享指定版本；分享全部现有及未来版本需要明确选择。课程规模下可先内嵌授权，授权量显著增长时再独立为集合。

可选保存一个仅所有者可编辑的工作草稿，包含 `base_version_id / content / draft_revision`。工作草稿可自动保存，但不能被问卷或题库引用；只有正式保存的版本可以引用。

`default_version_id` 只是新选题时的推荐值，任何现有问卷都不能在读取时动态跟随它。

### 4.2 question_versions 不可变题目版本

建议结构：

```json
{
  "_id": "ObjectId",
  "series_id": "ObjectId",
  "version_no": 3,
  "parent_version_id": "ObjectId or null",
  "restored_from_version_id": null,
  "derived_from_version_id": null,
  "created_by": "ObjectId",
  "created_at": "datetime",
  "change_note": "调整年龄范围",
  "content": {
    "type": "number",
    "title": "你的年龄",
    "num_min": 0,
    "num_max": 120,
    "integer_only": true
  }
}
```

上述字符串用于说明 BSON 字段类型；实际入库使用 ObjectId 和 datetime。

- 正式版本只新增，不提供覆盖内容或硬删除接口；JSON Schema 本身不能保证不可变，仍需服务层约束和测试。
- 同系列创建新版本时，父版本必须存在且属于该系列；允许从历史版本分支。
- 分享接收者不能在原作者系列里写版本；需要修改时，派生为自己的新系列，并用 `derived_from_version_id` 记录来源。
- 恢复示例：当前 v3 恢复 v1 的内容，创建 v4，`parent_version_id=v3`、`restored_from_version_id=v1`。旧 v1、v2、v3 全部保留。
- 版本号表示创建顺序，不代表唯一线性历史。系列原子计数器分配号码，允许失败产生空号；唯一索引兜底。

### 4.3 question_banks 与 question_bank_items

`question_banks` 保存题库所有者、名称、说明、元信息修订号和归档状态。第一版题库默认私有，题目共享独立处理；变更题目没有要求额外建设团队管理系统。

`question_bank_items` 保存 `bank_id / series_id / selected_version_id / revision / added_at`。一个题库对一个系列保留一个推荐条目，通过历史版本选择器访问其他版本。

题库条目升级仅更新自己的 `selected_version_id`，不能修改已有版本，也不能批量替换使用它的问卷。移除条目或归档题库只影响组织方式，不删除题目及答卷。

条目独立成集合，便于分页、去重和单条版本升级，也避免题库文档内的题目数组持续膨胀。

### 4.4 surveys 保留内嵌结构并增加来源

```json
{
  "schema_version": 2,
  "ever_published": true,
  "version": 7,
  "questions": [
    {
      "qid": "q3",
      "question_series_id": "ObjectId",
      "question_version_id": "ObjectId",
      "type": "number",
      "title": "你的年龄",
      "num_min": 0,
      "num_max": 120,
      "integer_only": true,
      "required": true,
      "order": 3,
      "jump_rules": []
    }
  ]
}
```

继续内嵌的理由：填写、校验和跳转都需要整份问卷，一次读取仍可获得完整结构；独立版本引用负责来源和复用，内嵌副本负责稳定展示。这是有明确用途的冗余。

后端根据版本内容生成副本，不能相信客户端同时传来的同名内容字段。数据库引用不会自动校验外部文档存在与权限，需由服务层执行。

### 4.5 responses 与 stats 的扩展边界

新答卷的 `snapshot.questions` 保留完整题目副本、全局系列和版本标识，继续以局部 `qid` 关联 `answers`。还可保存实际到达的 `visited_qids`，供跳过率等后续指标使用。

新答卷增加文档 `schema_version`，旧答卷保持原样。`schema_version` 与已有 `stats.stats_version` 是不同概念，后者仍表示统计计数编码格式，不能混用。

原整卷 `stats` 保留。跨问卷统计第一版直接读取答卷事实，不增加一个所有用户共用的全局计数器，以免共享权限、版本拆分和缓存一致性叠加。

### 4.6 建议索引

- `question_series`：`{owner_id, archived_at, updated_at}`，以及 `shared_with.user_id`。
- `question_versions`：`{series_id, version_no}` 唯一；`{parent_version_id}`；`{derived_from_version_id}`。
- `question_banks`：`{owner_id, updated_at}`。
- `question_bank_items`：`{bank_id, series_id}` 唯一；`{selected_version_id}`。
- `surveys`：`{questions.question_version_id, owner_id}`；需要系列级使用查询时补充系列标识索引。
- `responses`：`{snapshot.questions.question_version_id, survey_id, submitted_at}`；保留现有答卷索引。
- `legacy_question_bindings`：迁移来源组合键唯一，至少包含 `survey_id / survey_version / qid / snapshot_fingerprint`。

数组字段索引用于先筛选候选文档，进入数组后仍需对具体题目元素做匹配。不能仅因一个答卷包含目标版本，就把该答卷内所有题目的答案都算进去。

## 5. 发布锁定与并发控制

### 5.1 发布后永久锁定题目结构

首次发布原子设置 `ever_published=true`。已发布和已关闭问卷都禁止修改题目内容、约束、版本绑定、顺序、必答设置和跳转规则。收集开关、截止时间等管理操作仍可使用。

不能只判断 `status == published`，否则“关闭 → 修改 → 重新发布”就能绕过保护。题目需要改变时，复制为新的草稿和分享链接，旧问卷和旧答卷保持原样。

### 5.2 把服务端判断写入条件更新

当前保存接口的 `version` 乐观锁继续使用；发布、关闭也应使用条件更新并递增编辑版本。

结构保存的数据库过滤条件必须同时检查未锁定状态和预期版本，不能只在更新前读取状态。否则“发布”和“自动保存”并发时仍可能修改刚发布的问卷。

正式版本先新增成功，再让问卷绑定该版本；默认版本指针通过 `revision` 条件更新。指针更新冲突时保留已经新增的版本并明确提示，不能覆盖别人刚选定的默认版本。

当前开发环境是单机 MongoDB，方案不假定跨集合事务可用。单文档原子性不等于答卷插入、统计更新及其他集合修改整体原子；多步操作需幂等、可重试且允许对账。

## 6. 分享权限与使用情况

### 6.1 推荐权限规则

- 所有者管理题目、正式版本、分享和归档。
- 被分享用户可查看授权版本、在自己的问卷中使用，并按授权派生新题；不能覆盖原版本。
- 分享题目不自动分享使用者的问卷标题、链接、填写者身份和原始答案。
- 撤销分享阻止后续新增引用；已经保存到问卷的固定副本及已有答卷继续有效。不能靠撤销分享让别人已发布的问卷损坏。
- 已保存实例的重存与新引用要区分：重存不能因授权撤销而丢失原内容，新加入或替换版本仍须检查当前授权。

### 6.2 使用情况直接查问卷引用

通过 `surveys.questions.question_version_id` 查询精确版本，通过系列标识查询全部版本，返回问卷状态、绑定版本和可操作入口。不另维护一份必须与问卷同步的反向引用数组。

默认返回当前用户有权查看的问卷；其他用户私有问卷的名称和访问链接不公开。若产品需要展示跨用户引用数量，只提供政策允许的最小汇总信息。

题目修改界面展示使用情况，再提供“保存新版本”“另存独立题目”“保留工作草稿”等选择。题目第六项的“决定是否创建新版本”不能解释为允许覆盖已发布内容；只有工作草稿可原地编辑，正式版本始终保留。

## 7. 跨问卷统计设计

### 7.1 先明确版本和授权范围

默认按 `question_version_id` 汇总。系列页面可查看所有版本，但先分别展示；相同题干、相同选项结构或相同哈希都不能证明不同版本适合合并。

题型、选项含义、数值单位、量纲或采样约束变化时，强行合并可能产生错误结论。确需合并时，应明确选择版本、确认语义一致，并为选择题配置选项对应关系；该能力可作为后续增强，不作为第一版默认行为。

“所有问卷”应解释为调用者拥有统计权限的全部问卷。默认包含自己的问卷；如需题目作者查看其他使用者的统计，增加问卷所有者明确授予的、针对该题目的聚合统计权限。题目使用授权不能充当数据授权。

聚合授权可保存在问卷的 `question_stats_shares` 中，以 `question_version_id / grantee_id / permission=aggregate` 明确限定对象；只有问卷所有者能设置。查询时校验实际目标版本和被授权人，不能把“对问卷中某题有权限”扩展成对整份问卷全部题目有权限。

跨用户授权默认只开放计数、数值汇总和分布，不返回姓名、身份或逐条文本。原始文本列表仍按问卷所有权或单独明细授权分页获取。

### 7.2 聚合步骤

1. 确定有权统计的问卷集合以及授权题目范围。
2. 在 `responses` 中按问卷范围、版本标识和可选时间范围筛选。
3. 展开快照题目，对目标版本再次匹配。
4. 用该元素的 `qid` 关联当前答卷 `answers[qid]`，只统计真实存在且有效的答案。
5. 按题型汇总，返回版本、授权范围、覆盖问卷数、有效作答次数和各项结果。
6. 对旧答卷走第八节的兼容映射路径；新旧路径按答卷格式分开，避免重复计数。

单选统计每个选项的作答次数，多选展开选项后统计次数。数字统计有效数量、总和、平均值、最小值、最大值及直方图；跨问卷均值必须用 `总和 / 有效数量`，不能直接平均各问卷平均值。

示例验收：A 问卷的同版本年龄答案为 20、22，B 问卷为 30，总体均值应为 24；若只平均两个问卷均值会错误得到 25.5。

### 7.3 明确“次数”和“人数”

一个答卷中的一个题目实例是一条作答记录，统计键为 `(response_id, qid)`。同一题在同一问卷出现两次，应计为两次作答，同时可返回去重答卷数。

允许多次提交和匿名填写时，不能把作答次数宣称为跨问卷去重人数。选项占比默认以有效作答次数为分母，多选百分比之和可以超过 100%。

被跳过、未作答的题不计入有效作答数。旧快照不能可靠恢复全部到达路径，因此不能把缺失答案直接解释为“跳过”，也不对旧记录伪造到达率。

### 7.4 缓存策略

首版跨问卷统计用 MongoDB 聚合实现，避免直接相加当前按局部 `qid` 编码的整卷缓存。前端复用 ECharts 展示服务端汇总，不能为计算直方图而下载其他用户全部答卷。

如果后续增加缓存，键必须包含具体版本、授权范围及查询条件，并随授权撤销失效。性能优化放在统计口径正确之后。

原有整卷缓存也需补充故障与交错测试：当前 `revision` 条件重建不等于跨集合“恰好一次”。例如重建先读到已插入但尚未增量计数的答卷，随后又执行增量更新，仍可能重复计数。阶段二不能把该机制直接扩展成全局缓存；需以 `responses` 为事实源验证和修正恢复策略。

## 8. 旧数据迁移与兼容

### 8.1 迁移原则

保留旧问卷、分享链接、局部 `qid`、答案、答卷快照、提交时间和历史统计入口。旧答卷原文不批量改写；新版本来源只加到可变问卷和新写入的答卷中。

旧系统没有记录题目跨问卷身份和父版本关系，历史快照也缺少完整约束。这些信息不能通过迁移凭空补全，不能按同名题干或相同 `qid` 全局去重。

### 8.2 具体步骤

1. 记录基线提交，备份数据库，建立独立迁移测试库；先做 `dry-run`。
2. 为现存问卷的题目生成来源身份，迁移来源键至少包含 `survey_id + qid`；内容不发生改变。
3. 对同一编辑版本且快照内容吻合的答卷，可建立与当前题目版本的可验证关联；不能证明的历史内容独立导入为历史版本组。
4. 历史组以 `survey_id + survey_version + qid + snapshot_fingerprint` 区分；摘要只用于来源内部区分，不认定跨问卷为同题。缺失约束标记为未知，不套用当前规则重新校验旧答案。
5. 增加兼容集合 `legacy_question_bindings` 保存上述来源到新系列、版本的映射及完整性标记。旧快照仍原样保存，读取跨问卷统计时解析映射。
6. 不能证明父子关系的历史导入版本，父版本留空，标记来源不完整；需要关联为同一逻辑题目时人工确认，不制造虚假的线性历史。
7. 为已发布、已关闭或有历史发布证据的问卷设置永久结构锁；有答卷但发布标记不完整时保守锁定并记录原因。
8. 先生成题目版本，再用问卷编辑版本的条件更新写入来源字段，避免迁移覆盖并发编辑。索引和映射来源键保证重复运行不产生重复实体。
9. 校验问卷数、答卷数、答案、快照和旧统计；抽样填写旧链接；确认新旧统计路径不重叠。

迁移报告应区分“已验证关联”“独立历史导入”“需要人工确认”，不把未知信息默认为已恢复。旧数据仍可独立查看和按各历史组统计。

### 8.3 新旧请求兼容

旧的内联创建题目方式继续可用。服务端增加转换层，将内联题目保存为私有系列和正式版本，再生成原格式的问卷副本；从题库选择则直接引用已有版本。

旧格式保存草稿时，先按原问卷实例和内容确认是否复用既有绑定，不能每次自动保存都生成重复题目。已发布问卷的结构保存按新需求拒绝，这属于明确要求改变的行为。

新读路径兼容缺少来源字段的旧文档，写路径统一采用第二阶段结构。应用回退必须停止写入并使用备份或兼容代码，不能直接让旧保存接口覆盖新来源字段、绕过发布锁定。

## 9. API 调整建议

以下是拟定契约，实施时统一补充 Pydantic 请求响应模型、分页和错误码。

题目与版本：

```text
POST   /api/questions
GET    /api/questions?scope=mine|shared
GET    /api/questions/{series_id}
POST   /api/questions/{series_id}/versions
GET    /api/questions/{series_id}/versions
GET    /api/question-versions/{version_id}
POST   /api/questions/{series_id}/restore
POST   /api/question-versions/{version_id}/fork
POST   /api/questions/{series_id}/shares
DELETE /api/questions/{series_id}/shares/{user_id}
GET    /api/questions/{series_id}/usages?version_id=...
```

`POST /api/questions` 创建系列及首个正式版本；新版本请求携带父版本和修改说明；恢复请求携带当前基准和恢复来源。工作草稿若需服务端持久化，另加带修订号的草稿接口，不复用正式版本更新接口。

题库：

```text
POST   /api/question-banks
GET    /api/question-banks
PATCH  /api/question-banks/{bank_id}
GET    /api/question-banks/{bank_id}/items
POST   /api/question-banks/{bank_id}/items
PATCH  /api/question-banks/{bank_id}/items/{item_id}
DELETE /api/question-banks/{bank_id}/items/{item_id}
```

问卷与统计：

```text
POST   /api/surveys/{survey_id}/clone
GET    /api/question-versions/{version_id}/stats
GET    /api/questions/{series_id}/stats
PUT    /api/surveys/{survey_id}/question-stats-sharing
```

整卷创建、保存、发布、填写和统计的原路径保留。系列统计接口返回按版本分组结果；版本统计支持时间范围及问卷筛选，但所有筛选条件仍需服务端授权，不能让调用者用任意 `survey_ids` 绕过权限。

版本不存在用 404，未授权用 403，编辑版本冲突或已发布结构锁定用 409，非法题目结构或跳转规则保持明确的校验错误。

## 11. 实施顺序与验收门槛

### 第一步 固定基线和数据契约

记录现有提交、备份及第一阶段回归结果，确定身份字段、版本规则和权限口径，添加测试数据。先把“哪些内容不可变”写成测试。

验收：原功能可演示，新旧模型转换规则明确。

### 第二步 题目实体 版本与发布锁定

实现系列、正式版本、草稿、派生与恢复；新增来源解析层，落实发布和保存的并发保护。

验收：A 用 v1、B 用 v2；改 v2 不影响 A；关闭问卷后仍不能修改已发布内容；两个并发操作不能绕过锁。

### 第三步 分享 题库和使用情况

实现按版本授权、接收方复用、撤销、题库组织及版本选择；前端形成完整选题流程。

验收：分享后两人问卷确实引用同一版本；接收方不能覆盖原题；撤销后旧问卷仍正常，新引用被拒绝；题库升级不改变旧问卷。

### 第四步 兼容迁移与跨问卷统计

先在备份副本运行迁移，验证历史映射，再增加按具体版本和授权范围聚合的统计接口。

验收：统计不混入其他题目、版本或无权访问的问卷；新旧路径不重复计数；旧答卷和快照逐字段保留。

### 第五步 回归 文档与演示

完成自动测试、页面联调和演示数据，更新数据库设计、API、系统说明、关键逻辑、测试用例、完成报告及 AI 使用日志。

阶段一文档中“题目不会跨问卷共享”的假设要作为演进起点说明，不能继续当作当前设计结论；也不能删除原设计过程，让报告失去阶段对比。

## 12. 必须补充或调整的测试

- **复用**：一个版本被多个问卷引用；重复导入同一版本时局部 `qid` 不冲突；来源字段伪造被拦截。
- **共享**：未共享不可读不可引用；接收者能复用但不能改原题；版本范围、撤销、已有实例保留及新引用拒绝。
- **版本**：线性历史、从旧版本分支、跨系列父版本拒绝、恢复生成新版本、共享派生形成新系列、并发分配无重复版本号。
- **发布**：发布后不能改内容、约束、绑定及跳转；关闭后仍受保护；发布与自动保存并发只有合法结果；复制草稿不改变原卷。
- **题库**：添加去重、版本归属校验、推荐版本升级、移除条目不删除题目，原问卷不受影响。
- **跨卷统计**：同版本不同局部 `qid` 正确合并；同名无关题不合并；不同版本分组；加权均值、选项计数、空答案、跳过、重复实例和重复提交口径正确。
- **数据权限**：分享题目不获得私有问卷统计；聚合授权不能读取原始文本或身份；撤销统计授权后结果范围立即收缩。
- **迁移**：重复运行无重复实体；快照缺失约束不被补造；历史身份无法证实时独立保留；旧链接、原始答案、快照、总数和整卷统计一致。
- **原功能回归**：认证、四题型、跳转环检测与可达性、声明式校验、截止时间、匿名填写、去重、多人提交及统计重建。

现有 `test_submit.py` 中 `test_snapshot_captures_survey_at_submit_time` 明确期待发布后删题成功。应按新需求改为“原卷修改被拒绝，复制草稿后修改成功，旧答卷快照不变”，不能为保留原断言而放宽发布锁。

`tests/conftest.py` 的清理集合列表当前只有四个集合，新增集合和历史映射必须纳入测试隔离；迁移与回归只能操作明确配置的独立测试库。

## 13. 需要在实施前固定的产品解释

题目没有细化以下边界，本文先采用这些默认方案，后续若课程口径不同，只调整对应策略：

1. 分享默认针对指定版本，未来版本不自动公开；接收者不能修改原作者版本。
2. 不同正式版本默认分别统计，跨版本合并需要明确语义和映射规则。
3. 跨问卷统计覆盖全部有授权的数据；跨用户结果需问卷所有者另行授予聚合权限。
4. 正式版本始终不可变；“是否创建新版本”的选择仅影响是否把工作草稿正式保存，不允许覆盖已发布内容。
5. 归档、移出题库、撤销分享都不能破坏既有问卷及历史答卷。

这些规则共同保证第二阶段的新增复用能力不会破坏第一阶段的填写和历史数据。最终演示应至少串起“建题 → 分享 → 两份问卷复用 → 新建版本 → 旧卷不变 → 恢复历史 → 题库升级 → 跨卷统计”完整流程。
