# 数据库设计

## 1. 为什么用 MongoDB 而不是关系数据库

| 维度 | 关系数据库方案 | MongoDB 方案（本系统） |
|------|---------------|----------------------|
| 问卷结构 | 需要 survey / question / option / jump_rule 多张表，读取整份问卷要多次 join | 问卷 + 题目 + 跳转规则**内嵌为一个文档**，1 次查询拿到整份问卷 |
| 答卷结构 | 答案表需要"问卷快照表"才能保留问卷修改前的结构，多表关联 | 答卷文档**自带题目快照**，旧数据天然完整 |
| 题型扩展 | 新增题型要加表/加列，涉及 schema 迁移 | 题目字段是文档内的自由结构，新题型只是新字段组合 |
| 数据特征 | 问卷数据是树形、变长、异构的 | MongoDB 文档模型与之一一对应 |

**结论**：问卷系统"整份读写问卷、答卷需要固化问卷结构"的特性，恰好是文档数据库的
主场 —— 内嵌（embedding）替代 join、快照替代历史表。这正是"为什么不用关系数据库结构、
为什么适合 MongoDB"的核心论据。

## 2. 集合划分（4 个集合）

```
users      用户账号
surveys    问卷（题目 + 跳转规则内嵌）
responses  填写记录（含问卷快照，写入后不再修改）
stats      预聚合统计计数器（提交时 $inc 更新）
```

**为什么不是一个集合**：四类数据的读写模式完全不同 —— 用户高频点查、
问卷整体读写、答卷高频写入、统计高频聚合读取；拆开后各自的索引与一致性
策略独立，互不干扰。同时体现了"不把所有数据塞进一个集合"的要求。

## 3. 集合文档结构

### 3.1 users

```js
{
  _id: ObjectId,
  username: "alice",            // 唯一索引
  password_hash: "$2b$12$...",  // bcrypt 哈希，绝不存明文
  created_at: ISODate
}
```

不存"问卷列表"字段：通过 `surveys.owner_id` 查询即可，避免冗余与不一致。

### 3.2 surveys（问卷 + 内嵌题目）

```js
{
  _id: ObjectId,
  title: "大学生消费习惯调查",
  description: "...",
  owner_id: ObjectId,             // 索引
  allow_anonymous: false,
  allow_multiple_submissions: false,
  status: "draft",                // draft → published → closed → published
  published_at: ISODate | null,
  deadline: ISODate | null,
  share_token: "xLK5v-9p",        // 唯一索引，填写链接 /s/{token}
  version: 7,                     // 乐观锁版本号，每次修改 +1
  questions: [                    // 题目内嵌：整份问卷一次读取
    {
      qid: "q1",                  // 问卷内唯一短 ID，跳转规则引用它
      type: "single",             // single | multiple | text | number
      title: "你的性别",
      required: true,
      order: 1,
      options: ["男", "女", "其他"],          // single / multiple
      min_select: 1, max_select: 2,          // multiple 选择数量限制
      text_min_len: 1, text_max_len: 50,     // text 字数限制
      num_min: 0, num_max: 120, integer_only: true, // number 数值限制
      jump_rules: [                          // 跳转规则内嵌，数据驱动
        { when: { op: "eq", value: "男" }, goto: "q3" },
        { when: { op: "eq", value: "女" }, goto: "q2" }
      ]
    }
  ],
  created_at: ISODate,
  updated_at: ISODate
}
```

**为什么题目内嵌而不是单独 questions 集合**：
- 问卷是"整体读写"的：编辑、发布、填写入口都读整份问卷；
- 题目不会跨问卷共享，不存在多对多引用；
- 内嵌后读取整份问卷 = 1 次查询，无 join；
- 这正是文档模型相对关系模型的优势场景。

**version 字段**：乐观锁。保存时 `where version = 旧值`，不匹配说明问卷已被
其他页面修改 → 返回 409 冲突，前端提示刷新。并发编辑不互相覆盖。

### 3.3 responses（答卷 = 快照 + 答案，设计核心）

```js
{
  _id: ObjectId,
  survey_id: ObjectId,            // 复合索引 {survey_id: 1, submitted_at: -1}
  survey_version: 1,              // 提交时问卷的版本号
  snapshot: {                     // ★ 提交瞬间的问卷题目快照
    title: "大学生消费习惯调查",
    questions: [
      { qid: "q1", type: "single", title: "你的性别", options: ["男","女","其他"] }
      // 只保留统计所需的精简结构
    ]
  },
  answers: {
    "q1": ["男"],                 // single/multiple：数组
    "q3": "20"                    // text/number：字符串（数字按原样存字符串）
  },
  respondent: {
    user_id: ObjectId | null,     // 匿名答卷为 null
    username: "bob" | null,
    anon_id: "anon-xxxx" | null   // 匿名答卷的浏览器指纹
  },
  respondent_key: "u:67f...",     // 去重键，见下
  submitted_at: ISODate,
  spent_seconds: 42
}
```

**快照的意义（报告重点）**：
- 问卷发布后被修改（第二阶段必然发生），旧答卷依然可以按**提交时的题目结构**
  准确统计 —— 因为每份答卷自带结构副本；
- 直接满足"旧数据必须保留"的硬性要求；
- 统计重建（慢通道）只依赖 snapshot，与问卷当前状态解耦。

**answers 只保存实际到达的题目**：跳转引擎先模拟整卷流程得到 visited 集合，
被跳过的题目即使答案被伪造提交也不会入库。

**respondent_key 原子去重**：不允许重复填写时，
登录用户 = `"u:" + user_id`，匿名用户 = `"a:" + anon_id`；
配合唯一索引 `{survey_id, respondent_key}`，并发重复提交由数据库原子拒绝（409）。

### 3.4 stats（预聚合计数器）

```js
{
  _id: ObjectId,
  survey_id: ObjectId,            // 唯一索引
  total: 3,
  questions: {
    "k_<题目摘要>": {
      counts: { "k_<选项摘要>": 2 },
      labels: { "k_<选项摘要>": "男" }
    },
    "k_<数字题摘要>": { num_sum: 67, num_count: 3 }
  },
  revision: 12,
  stats_version: 2
}
```

**统计文档的设计**：
1. **题目和选项用稳定摘要键计数**：更新路径不含原始题目 ID 或选项文本，避免 `.` / `$` 等非法字段名；摘要不依赖选项顺序，标签单独存储；
2. **数字用 sum/count 而非直接存均值**：`$inc` 只能做加法，存"和 + 个数"
   使平均值可以原子增量更新。
3. **revision 保护重建**：条件替换统计文档时检查版本号；发生并发计数更新时重新读取并重试。

**为什么预聚合（双通道的"快通道"）**：提交时 O(1) 更新，统计页 O(1) 读取，
无需每次统计都扫全量答卷；完整明细仍可查 responses，并支持基于答卷快照重建（慢通道），
两通道结果可互相校验（`test_rebuild_matches_fast_channel`）。

## 4. 索引设计

| 集合 | 索引 | 类型 | 用途 |
|------|------|------|------|
| users | {username: 1} | 唯一 | 注册查重 / 登录点查 |
| surveys | {owner_id: 1} | 普通 | "我的问卷"列表 |
| surveys | {share_token: 1} | 唯一 | 填写链接点查 |
| responses | {survey_id: 1, submitted_at: -1} | 复合 | 按问卷查答卷明细（时间倒序） |
| responses | {survey_id: 1, respondent_key: 1} | 唯一 | 原子防重复提交 |
| stats | {survey_id: 1} | 唯一 | 统计点查 |

## 5. 数据完整性

- **$jsonSchema 校验器**：四个集合均挂 JSON Schema 校验器，数据库层拒绝
  非法文档（如缺少必填字段、status 非法值）；
- **单文档原子性**：答卷一次性 insert，不存在"半份答卷"；
- **原子自增**：stats 用 `$inc` 更新，100 并发提交测试计数精确 = 100；
- **乐观锁**：surveys.version 防并发编辑覆盖；
- **服务端唯一可信边界**：截止时间 / 发布状态 / 重复提交 / 答案合法性
  全部在提交接口服务端强制校验，前端校验只是体验优化。
